# CarIndex vehicle-data — P1 buyer view, SUV ~EGP 2M slice

P2 (vehicle data) output for P1 (buyer-decision product). P1 reads **one file** and does not need to know the underlying spreadsheets.

## What P1 consumes

| File | Use |
|---|---|
| `views/p1_suv_2m.json` | The interface. One object per model (`models[]`), each with `price`, `specs`, `registration`, `freshness`, `conflicts`, `gaps`. Schema id `carindex.p1.buyer_view/v1`. |
| `views/p1_suv_2m_summary.csv` | One row per model, for list and shortlist screens. Generated from the same build. |
| `views/price_history.csv` | Every price series across all snapshots (prev → latest, full series). |
| `review/review_queue.csv` | Items that need a human decision. P1 should treat them as open, not as resolved. |

All four files are generated by `scripts/build_p1.py`. Do not edit them by hand.

### Rules P1 must follow when reading the JSON

- **The model is canonical.** `model_id` is the key. Trims are evidence attached to a model.
- **IDs are `PROVISIONAL`** (decisions D3/D4 are still open). Do not build public URLs from them.
- **`price.price_from`** is the lowest official price in the latest model-year cohort that has any numeric price. `status` takes one of these values:
  - `RESOLVED`: `value` is set.
  - `RESOLVED_RANGE`: sources differ by ≤ EGP 5,000. `value_min` and `value_max` are given, and there is no single `value`.
  - `CONFLICT`: the cheapest trims disagree. `value` is null and `candidate_min` is given. Show the conflict. Never average it.
- **`price.source_stated_changes`** lists official price changes as Hatla2ee states and dates them (its 'Latest Changes' section): old → new with the source's own date. These are source claims, not our observations.
- **Official price and market price are separate series** and are never merged. `market_premium` is market minus official from the same source row.
- **`official.status` per trim** takes one of these values:
  - `AGREED`: 2 or more sources give the same value. Confidence HIGH.
  - `SINGLE_SOURCE`: one source only. Confidence MEDIUM.
  - `NEAR_AGREEMENT`: sources differ by ≤ EGP 5,000. Confidence MEDIUM.
  - `CONFLICT`: sources differ by more than that. Confidence LOW.
  - `NO_NUMERIC_PRICE`: no source gives a numeric price.
- **Every value carries provenance.** Each value has `source`, `url`, `observed_at`, and `ref` (the file and row it came from). `source_effective_date` appears only where the source states a date (EgyCar only). It is never back-filled.
- **Registration figures count first licences, not sales.** Use them for adoption level (`registrations_in_window`, `rank_in_slice`, `share_of_slice_registrations`), momentum (`momentum.yoy_change`), time on the market (`first_seen_month`), and the powertrain actually registered (`powertrain_mix_in_window`). Do not present them as reliability, resale value or satisfaction. No such data exists.
- **`gaps[]` lists known unknowns.** Examples: `SINGLE_SOURCE_MODEL`, `FROM_PRICE_IN_CONFLICT`, `REGISTRATION_UNLINKED`, `PRICE_RULE_NOT_MET`, `NO_OFFICIAL_PRICE`. A recommendation that depends on a gapped field has to say so.
- **Specs:** use `specs.trim_pages` (trim-detail pages, latest full refresh) first, and fall back to `specs.attributes` (S0, 2026-09-10). In both, values that differ by trim or source are all listed (`MULTIPLE_VALUES`) and none is chosen.

## Slice definition (`config/slice_suv_2m.json`)

A model is in the slice when it meets all three conditions:

- It is an SUV or crossover (`body_type_normalized` contains "SUV").
- It has a trim-level S0 official price in the EGP 1.6M–2.4M band.
- It has ≥ 500 passenger first registrations from 2025-09 to 2026-08 through an ACCEPTED registration alias. Jun 2026 is missing from the source.

Result: 21 models in the slice. 3 more are kept with `in_slice=false` and a gap:

- Citroën C5 Aircross: registration "C5" is ambiguous.
- BYD Song L DM-i: registration "Song L" is BEV only.
- BYD Song Plus: it has only an aggregate "Other Trims" price, and that price's column is suspect.

## Identity and crosswalks

- `registry/models.csv`: model IDs.
- `crosswalk/scrape_aliases.csv`: price/spec names → `model_id`.
- `crosswalk/registration_aliases.csv`: registration `Brand|Consolidated` → `model_id`, with `status` (ACCEPTED / REJECTED_*), `match_rule` and `confidence`. MEDIUM aliases are in the review queue.
- `crosswalk/trim_synonyms.csv`: the only non-mechanical trim-label fixes (2 misspellings).

## Refresh pipeline (no LLM in the routine path)

```
sitemaps ──► discover.py ──► discovery_events.csv + discovery_triage.csv   (new launches)
model pages (42) ─┐
trim pages (~n) ──┴► fetch_snapshot.py fetch ► raw/ (CI artifact, 90 days)
                                            └► evidence.jsonl.gz (git; re-parseable forever)
                     ► parse / specs  ► observations_parsed.csv, specs_parsed.csv
                     ► detect_changes.py ► change_events.csv   (price / trim / spec / source health)
                     ► build_p1.py ► views/p1_suv_2m.json (+ summary, price_history.csv), review/review_queue.csv
```

- **Run it:** in GitHub, go to Actions → "vehicle-data refresh" → Run workflow (`full` = prices + specs, `prices` = model pages only). You can also push any change to `vehicle-data/refresh.request`. Locally, run `scripts/refresh.sh full` from a machine that can reach the three sites.
- **What each run does:** it creates `snapshots/S<n>_<date>/` with `run_report.json` (pages fetched, bytes downloaded, seconds, event counts, `llm_calls=0`) and commits the parsed files back to the branch.
- **Transport is plain HTTP.** No browser or extension is needed: all three sites render prices and specs server-side, and every page used is allowed by the site's robots.txt (checked 2026-09-25; Hatla2ee `/api/` is disallowed and not used). Requests run one at a time with a 1-second delay.
- **Where Claude or a human is needed:** only `review/review_queue.csv`, `change_events.csv` rows with confidence LOW or `material=True`, and discovery triage rows that fall in the slice band. Nothing is promoted automatically.
- **Schedule:** off until D10 (cadence) and D14 (source terms of use) are decided. Uncomment the `schedule:` block in `.github/workflows/vehicle-refresh.yml` to turn it on.

## Rebuild

```
python3 scripts/build_p1.py --master inputs/s0_slice_master.csv --reg inputs/registration_slice.json --as-of YYYY-MM-DD
```

`reg_payload.json` is the `<script id="payload-data">` JSON inside `Vehicle_Registration_Explorer.html`: Drive `1jJsabEDwGbrBy2eAjDnnNU2ULeaQ1Ala`, modified 2026-09-24, 591,177 archive rows, months 2021-02 to 2026-08. The JSON output's `inputs[]` records the SHA-256 of every input.

The output is deterministic: two runs on the same inputs are byte-identical.
